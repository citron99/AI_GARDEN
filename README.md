# AI-помощник садовода — MVP 0.1

Первый запускаемый срез проекта по техническому заданию: REST API для растений, фотографий, безопасной AI-диагностики и демонстрационного каталога товаров.

## Возможности

- регистрация с подтверждением email, восстановление пароля, rotatable refresh-сессии,
  отзыв токенов, rate limit и JWT-авторизация;
- личный профиль и изоляция данных пользователей;
- структура «пользователь → сады → растения»;
- создание и просмотр растений;
- загрузка 1–5 изображений (JPEG, PNG или WebP, до 10 МБ каждое);
- создание диагностического обращения по симптомам;
- до трёх вероятных причин, уточняющие вопросы и безопасные действия;
- история диагностик, ответы на уточняющие вопросы и версии повторного анализа;
- коммерческие предложения отделены от диагностического ответа;
- переход к партнёру использует подписанный обезличенный click ID и контролируемый
  redirect; postback продажи требует отдельный ротируемый partner key;
- загрузки ограничены rate limit и пользовательской квотой хранения, старые
  непривязанные фотографии автоматически удаляются через retry-outbox;
- Swagger UI: `http://localhost:8000/docs`.
- пользовательский веб-интерфейс: `http://localhost:8000/`.

Доступны два AI-провайдера: `mock` для разработки и `openai` для реального
мультимодального анализа через Responses API. OpenAI-провайдер читает очищенные
изображения, учитывает растение, регион, симптомы и ответы пользователя и
валидирует ответ через строгую схему `DiagnosisResult`. В результат попадают
только URL из активного управляемого каталога проверенных источников.

Политика передачи данных внешнему AI описана в [PRIVACY.md](PRIVACY.md). Responses
API вызывается с `store=False`; для пользователя передаётся только обезличенный
HMAC safety identifier. Для AI создаётся временная JPEG-копия не более 2048 px,
при этом сохранённая очищенная фотография не уменьшается.

Качество входа (`input_status`) отделено от результата анализа (`analysis_outcome`).
AI может безопасно отказаться со статусом `poor_quality`, `not_a_plant` или
`insufficient_data`; для здорового растения возвращается `no_visible_problem` без
выдуманных причин, а `possible_problem` допускает 1–3 гипотезы. По умолчанию действует лимит
5 новых диагностик в месяц и 3 повторных анализа на диагностику. Токены, задержка,
примерная стоимость и безопасный тип ошибки сохраняются в `ai_request_logs`.

`evals/` содержит инфраструктуру оценки, но не фиктивную экспертную разметку.
До добавления минимум 200 проверенных агрономом случаев validation gate намеренно
завершается ошибкой, поэтому проект не заявляет измеренную точность диагностики.

## Запуск

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
Copy-Item .env.example .env
pip install --require-hashes -r requirements.lock
alembic upgrade head
uvicorn app.main:app --reload
```

Для локальной демонстрации можно создать или восстановить подтверждённые аккаунты
садовода, партнёра и администратора:

```powershell
python -m scripts.seed_demo_users
```

Команда выводит локальные данные входа и намеренно отказывается работать при
`ENVIRONMENT=production`. Не используйте эти пароли в опубликованной среде.

Или через Docker:

```powershell
Copy-Item .env.example .env
docker compose up --build
```

## Миграции базы данных

Схема базы управляется Alembic. Приложение больше не создаёт таблицы через
`Base.metadata.create_all()` при запуске.

Применить все миграции:

```powershell
alembic upgrade head
```

Откатить последнюю миграцию:

```powershell
alembic downgrade -1
```

Создать миграцию после изменения ORM-моделей:

```powershell
alembic revision --autogenerate -m "описание изменения"
alembic upgrade head
```

Для базы, ранее созданной старой версией приложения без таблицы
`diagnosis_photos`, сначала сделайте резервную копию, затем отметьте базовую
схему и примените новую миграцию:

```powershell
alembic stamp 0001_base
alembic upgrade head
```

Docker-контейнер автоматически выполняет `alembic upgrade head` перед запуском API.

## Тесты

```powershell
pytest
npm install
npx playwright install chromium
npm run test:e2e
```

Python suite проверяет API, безопасность, миграции и полноту RU/LV/EN-переводов.
Playwright выполняет реальный Chromium-сценарий «регистрация → сад → растение →
настоящая PNG-фотография → диагностика → ответы и версия → отзыв → товар →
повторяющееся напоминание» в Desktop Chrome и мобильном Pixel 5. Сценарий проверяет
отсутствие горизонтального overflow и ошибок консоли, а также запускает axe WCAG
2/2.1 A/AA после динамического результата. В CI браузер и системные зависимости
устанавливаются отдельным `browser-e2e` job; временные БД изолированы по PID.

## Основной сценарий

1. `POST /api/v1/auth/register` — зарегистрироваться; вне test-среды подтвердить email,
   затем войти. Доступны refresh/logout и одноразовое восстановление пароля.
2. `POST /api/v1/gardens` — создать сад.
3. `POST /api/v1/plants` — добавить в него растение.
4. `POST /api/v1/plants/{id}/photos` — загрузить фотографии.
   `GET /api/v1/photos/{id}` — безопасно получить свою фотографию.
5. `POST /api/v1/diagnoses` — описать проблему.
6. `GET /api/v1/diagnoses/{id}` — получить сохранённый результат.
7. `GET /api/v1/recommendations/{id}/products` — отдельно получить рекламные предложения.
8. `GET /api/v1/plants/{id}/diagnoses` и `/history` — получить историю растения.
9. `GET /api/v1/diagnoses/{id}/questions` — получить вопросы текущей версии.
10. `POST /api/v1/diagnoses/{id}/answers` — ответить и автоматически создать новую версию.
11. `POST /api/v1/diagnoses/{id}/reanalyze` — выполнить повторный анализ.
12. `POST /api/v1/diagnoses/{id}/feedback` — сохранить обратную связь.
13. `POST/GET /api/v1/plants/{id}/care-events` — добавить или прочитать записи ухода.
14. `PATCH/DELETE /api/v1/care-events/{id}` — исправить или удалить запись журнала.
15. `POST/GET /api/v1/plants/{id}/reminders` и `PATCH/DELETE /api/v1/reminders/{id}` — управлять напоминаниями.
16. `GET /api/v1/calendar?start=...&end=...` — получить календарь ухода, сезонных задач и погодных рисков.
17. `GET /api/v1/gardens/{id}/weather` — получить прогноз Open-Meteo и погодные предупреждения для сада.
18. `PATCH/DELETE /api/v1/gardens/{id}` — изменить или удалить сад со связанными растениями.
19. `PATCH/DELETE /api/v1/plants/{id}` — изменить или удалить растение, его фотографии и историю.
20. `POST /api/v1/diagnoses/async` — создать устойчивое задание фоновой диагностики.
21. `GET /api/v1/diagnosis-jobs/{id}` — получить статус `queued`, `running`, `succeeded` или `failed`.

В development используется `DIAGNOSIS_EXECUTION_MODE=sync`: persistent job создаётся и выполняется локально, что упрощает запуск без Redis. Production требует `DIAGNOSIS_EXECUTION_MODE=celery`; `compose.prod.yaml` запускает отдельные API, Celery worker, Redis и PostgreSQL. В Redis передаётся только UUID задания — фотографии и диагностический payload остаются в основной базе и общем защищённом хранилище.

Worker использует late acknowledgement, атомарный lease и уникальный execution token,
возвращает задачу в очередь при аварийном завершении, ограничивает время выполнения и
повторяет временные ошибки AI-провайдера до двух раз. Создание диагностики, ответы и
повторный анализ проходят через единый job-flow. Итоговый статус хранится в
`diagnosis_jobs`, поэтому не зависит от срока хранения результатов Redis.

Списки садов, растений, диагностик, журналов, напоминаний, уведомлений и
административных сущностей принимают ограниченные `offset`/`limit`. Ежедневная
maintenance-задача удаляет старые завершённые jobs, уведомления, технические AI-логи,
Telegram updates, billing events и истёкшие session/action tokens; сроки задаются
отдельно по типам данных в конфигурации.

Браузерный smoke-сценарий запускается командой `npm ci && npx playwright install chromium && npm run test:e2e`.

Чистый архив для передачи или публикации создаётся вне каталога проекта:

```powershell
python scripts/package_release.py --output ..\AI_Garden_clean.zip
```

## Административная панель

Роль администратора невозможно указать при регистрации или через публичный API. После создания пользователя роль назначается из доверенной консоли:

```bash
python -m app.admin_cli grant admin@example.com
python -m app.admin_cli revoke admin@example.com
```

Read-only endpoints `/api/v1/admin/overview`, `/users`, `/diagnosis-jobs` и `/ai-requests` требуют `is_admin=true`. Панель показывает агрегаты, состояния worker и технические AI-метрики, но не возвращает фотографии, локальные пути, симптомы, полный результат диагностики, payload заданий или хэши паролей.

Администратор управляет партнёрами и товарами через `/api/v1/admin/partners` и
`/api/v1/admin/products`. Товар проходит `draft → pending → approved/rejected`.
Диагностическая рекомендация возможна только по одобренному товару и подтверждённому
правилу «культура → проблема → безопасное действие → регион» с действующей регистрацией;
средства защиты растений без этих данных исключаются. Каждый такой блок имеет явную
маркировку «Реклама партнёра» и не влияет на AI-результат. `POST /api/v1/products/{id}/lead` идемпотентно фиксирует
переход, а `/api/v1/admin/leads` возвращает только товар, источник, ID диагностики
и дату — без симптомов, фотографий и персональных данных пользователя.

Для регулируемых средств предусмотрен версионируемый локальный реестр. Администратор
импортирует нормализованный снимок официального источника через
`POST /api/v1/admin/regulated-products/import`, просматривает записи через
`GET /api/v1/admin/regulated-products` и связывает их с правилами через
`POST /api/v1/admin/product-recommendation-rules`. Каждая запись хранит источник,
версию, контрольную сумму, статус и срок действия. Отозванная, истёкшая или
исчезнувшая из полного снимка регистрация немедленно исключает связанные рекомендации;
дополнительная ежедневная проверка выполняется maintenance-задачей. Импорт не является
автоматическим получением данных с VAAD/EU: формат и право повторного использования
официального набора должны быть утверждены до подключения live-коннектора.
[EU Pesticides API](https://data.europa.eu/data/datasets/pesticides?locale=en)
предоставляет данные о действующих веществах и MRL и потому не используется как
доказательство регистрации конкретного товара в Латвии. Национальная сверка должна
опираться на актуальный реестр VAAD; обнаруженная [публичная публикация VAAD](https://www.vaad.gov.lv/lv/latvijas-republika-registreto-augu-aizsardzibas-lidzeklu-saraksts)
представлена веб-реестром и ежегодным списком/PDF, а не документированным открытым API.

## Кабинет садового центра

Администратор назначает зарегистрированного пользователя сотрудником организации
через `POST /api/v1/admin/partners/{id}/members`. Роли `owner` и `editor` могут
создавать и включать/отключать товары своей организации; `viewer` имеет только
просмотр. Кабинет использует `/api/v1/partner/me`, `/overview`, `/products` и
`/leads`. Все запросы принудительно ограничены организацией текущего сотрудника.

Партнёрская аналитика показывает количество товаров и переходов, а список лидов —
только товар, источник и дату. Email клиента, ID пользователя и диагностики,
симптомы, ответы и фотографии через API партнёра не возвращаются.

Переход и подтверждённая конверсия разделены. Владелец или редактор партнёра может
заявить продажу через `POST /api/v1/partner/leads/{id}/conversion`, передав только
внутреннюю ссылку на заказ без данных клиента и сумму. Администратор подтверждает
или отклоняет её через `PATCH /api/v1/admin/leads/{id}/conversion`. Стоимость лида
фиксируется по тарифу партнёра только после подтверждения. Периодические счета
создаются через `POST /api/v1/admin/partners/{id}/invoices`; один подтверждённый лид
нельзя включить повторно, а пересекающиеся расчётные периоды блокируются. Партнёр
видит свои счета в `GET /api/v1/partner/invoices`.

Перед выпуском счёта администратор заполняет юридическое название, регистрационный
номер, адрес и бухгалтерский email партнёра. Реквизиты выставителя задаются через
`B2B_INVOICE_*`; в production эти реквизиты обязательны только при
`B2B_INVOICING_ENABLED=true`. При выпуске сохраняются неизменяемые снимки сторон и
строк начислений, номер вида `AG-YYYY-NNNNNNNN`, версия документа, SHA-256 PDF и сам
неизменяемый PDF-объект в приватном local/S3-хранилище. PDF доступен только
администратору через `GET /api/v1/admin/partner-invoices/{id}/pdf` и сотруднику той же
организации через `GET /api/v1/partner/invoices/{id}/pdf`. При чтении проверяются
хеш снимка данных, MIME, размер и SHA-256 сохранённых байтов; обновление ReportLab или
шрифта не меняет уже выпущенный документ. Изменение текущих реквизитов партнёра также
не переписывает его.

Аннулирование выставленного счёта через
`PATCH /api/v1/admin/partner-invoices/{id}` требует причины и создаёт отдельный
неизменяемый операционный документ с номером `AG-CN-YYYY-NNNNNNNN`, версией и
SHA-256. Его можно получить через
`GET /api/v1/admin/partner-invoices/{id}/cancellation.pdf` либо, сотруднику той же
организации, через `GET /api/v1/partner/invoices/{id}/cancellation.pdf`. Исходный
счёт при этом остаётся неизменным.

Администратор отправляет документ на email из неизменяемого снимка через
`POST /api/v1/admin/partner-invoices/{id}/send`. Повторная отправка требует явного
`confirm_resend=true`; каждая попытка сначала фиксируется со статусом `pending`, после
коммита публикуется в Celery и атомарно переходит в `sending`, затем в `sent`, `logged`
или `failed`. Повторная доставка одной задачи не отправляет письмо второй раз, а beat
переиздаёт оставшиеся `pending` и переводит зависшие `sending` в `unknown`. Журнал
доступен только администратору через
`GET /api/v1/admin/partner-invoices/{id}/deliveries`. В development письмо не
имитируется как доставленное: записывается статус `logged`; production использует
настроенный SMTP с STARTTLS и PDF-вложением.

Для сверки оплаты администратор импортирует нормализованные банковские операции через
`POST /api/v1/admin/partner-payments/import`. Операция идемпотентна по паре
`source + external_id`. Счёт становится оплаченным только при единственном точном
номере `AG-YYYY-NNNNNNNN` в назначении, статусе `issued` и полном совпадении суммы и
валюты; остальные записи получают `unmatched` и доступны для проверки через
`GET /api/v1/admin/partner-payments`. Это импорт уже подготовленной выгрузки, а не
заявление о подключённом банковском API.

Запись `unmatched` можно один раз разрешить через
`PATCH /api/v1/admin/partner-payments/{id}`: сопоставить с выставленным счётом либо
отклонить. Ручное сопоставление также требует полного совпадения суммы и валюты,
блокирует строку счёта от конкурентной оплаты и сохраняет администратора, время,
примечание и audit log. Уже принятое решение переписать через API нельзя.

Прямой перевод счёта в `paid` через PATCH запрещён. Ручная оплата регистрируется
через `POST /api/v1/admin/partner-invoices/{id}/manual-payment` с внешним ID,
способом, датой проводки и примечанием; при этом создаются полноценная запись
`PartnerPayment` и audit log. Поэтому оплаченный статус всегда имеет проверяемое
основание.

Это операционный B2B PDF, а не заявление о налоговой сертификации. До использования
как юридически значимого счёта или кредит-ноты для выбранной страны бухгалтер/юрист
должен утвердить нумерацию, налоговые строки, правила аннулирования/кредит-нот и при необходимости
формат e-invoice, банковскую сверку и интеграцию с бухгалтерией.

## Подписки и Stripe

По умолчанию `BILLING_PROVIDER=disabled`: тарифы видны, но реальная оплата не
имитируется. Для Stripe задайте `BILLING_PROVIDER=stripe`, live API key,
подписочный Price ID, webhook secret и собственные HTTPS URL возврата. В production
тестовый ключ и шаблонные URL отклоняются при старте.

- `GET /api/v1/billing/plans` — тарифы без секретных Stripe ID;
- `GET /api/v1/billing/subscription` — статус текущего пользователя;
- `POST /api/v1/billing/checkout` — Stripe-hosted Checkout для серверного Price ID;
- `POST /api/v1/billing/portal` — Customer Portal для управления подпиской;
- `POST /api/v1/billing/stripe/webhook` — подписанный webhook без JWT.

Тариф активируется только по подписанным событиям `customer.subscription.*`, а не
по возврату браузера с Checkout. Raw body проверяется по `Stripe-Signature` с
пятиминутным окном, event ID обрабатывается идемпотентно, неизвестный Price не даёт
Pro-доступ. Активный Pro повышает месячный лимит с `FREE_DIAGNOSES_PER_MONTH` до
`PRO_DIAGNOSES_PER_MONTH`. Номера карт обрабатываются на стороне Stripe и в API
AI Garden не поступают.

Настройка основана на официальных руководствах Stripe по
[Checkout subscriptions](https://docs.stripe.com/payments/checkout/build-subscriptions)

## Telegram-бот

По умолчанию `TELEGRAM_ENABLED=false`. После создания бота через BotFather задайте
`TELEGRAM_BOT_TOKEN`, username и отдельный случайный `TELEGRAM_WEBHOOK_SECRET`.
Публичный webhook должен вести на
`https://your-domain.example/api/v1/telegram/webhook`. Зарегистрируйте его методом
`setWebhook`, передав тот же `secret_token` и ограничив обновления сообщениями.

Пользователь создаёт одноразовую ссылку через `POST /api/v1/telegram/link` либо
веб-интерфейс. Код действует 10 минут, содержит 192 бита случайности и хранится в
БД только как SHA-256. Deep link имеет вид
`https://t.me/<bot>?start=<code>`. Привязка разрешена только из личного чата.

Команды:

- `/plants` — растения пользователя;
- `/today` — незавершённые напоминания на текущий день;
- `/unlink` — отключить Telegram;
- `/help` — справка.

Webhook сверяет `X-Telegram-Bot-Api-Secret-Token`, ограничивает размер тела и
идемпотентно сохраняет `update_id`. Если отправка ответа временно не удалась,
Telegram может повторить update: сохранённый ответ отправится ещё раз без повторного
выполнения команды. Официальные требования: [Telegram Bot API](https://core.telegram.org/bots/api)
и [deep linking](https://core.telegram.org/bots/features#deep-linking).

Параметр `include_weather=true` у `/api/v1/calendar` добавляет предупреждения о заморозке, жаре, сильном ветре, осадках и необходимости проверить полив. Прогноз кэшируется на 30 минут; во внешний погодный сервис передаётся только название местоположения для геокодирования и затем координаты, но не данные пользователя или растений.

Веб-интерфейс содержит отдельный экран календаря с выбором периода и группировкой событий по дням. Если Open-Meteo временно недоступен, интерфейс повторяет запрос без погоды и продолжает показывать журнал ухода и напоминания.

Календарь также автоматически добавляет локализованные сезонные работы: планирование
посевов, весенний осмотр, подготовку почвы, проверку поздних заморозков, летний
фитосанитарный осмотр, осеннюю уборку и подготовку к зиме. Celery Beat раз в час
создаёт дедуплицированные уведомления о задачах ближайших 24 часов, сезонных работах
и погодных рисках. Они доступны в `GET /api/v1/notifications`, отмечаются прочитанными
через `PATCH /api/v1/notifications/{id}/read` и при подключённом Telegram отправляются
ботом с повторными попытками без повторной доставки успешных сообщений.

## Проверенная база знаний и семантический поиск

Источники хранятся в таблицах `knowledge_sources` и `knowledge_chunks`. Для каждого
источника обязательны дата проверки и следующего пересмотра, имя/роль проверяющего,
основание использования, версия, HTTPS-ссылка и признак активности. Просроченные
материалы автоматически исключаются. Администратор может синхронизировать встроенный набор через
`POST /api/v1/admin/knowledge/sync`, просматривать его через
`GET /api/v1/admin/knowledge/sources` и добавлять или обновлять проверенные материалы
через `POST /api/v1/admin/knowledge/sources`.

В production используются OpenAI `text-embedding-3-small`, PostgreSQL pgvector,
cosine distance и HNSW-индекс. Размерность настраивается через
`KNOWLEDGE_EMBEDDING_DIMENSIONS` (по умолчанию 256). SQLite/test используют
детерминированный локальный векторизатор без сетевых запросов. Результат AI получает
только ссылки из активного управляемого каталога; произвольные ссылки модели удаляются.
Для production используйте `compose.prod.yaml`, задав `PUBLIC_DOMAIN`, HTTPS
`PUBLIC_BASE_URL`, `DATA_CONTROLLER_NAME`, `PRIVACY_CONTACT_EMAIL`, `JWT_SECRET`,
`POSTGRES_PASSWORD`, `AI_PROVIDER=openai`, `OPENAI_API_KEY`, приватное S3-совместимое
хранилище и SMTP. Шаблонные секреты и `AI_PROVIDER=mock` в production отклоняются.
Caddy завершает TLS; API не публикуется напрямую, проверяет Host и выставляет HSTS.
Фотографии хранятся как приватные объекты и выдаются только владельцу через короткую
подписанную ссылку либо защищённый streaming-ответ. `/health/live` проверяет процесс,
а `/health/ready` — БД, миграции, Redis и доступность worker.

Дополнительные compose-файлы включают функции явно: `compose.core.yaml` оставляет
`PARTNER_COMMERCE_ENABLED=false` и `B2B_INVOICING_ENABLED=false`, а
`compose.commerce.yaml` включает оба коммерческих модуля. Например, базовый запуск:
`docker compose -f compose.prod.yaml -f compose.core.yaml up -d`; коммерческий запуск:
`docker compose -f compose.prod.yaml -f compose.commerce.yaml up -d`. Отключённые
маршруты коммерции не регистрируются, а API счетов дополнительно возвращает 404 при
выключенном B2B-флаге.

Перед переключением существующей установки с `STORAGE_BACKEND=local` на S3 сначала
выполните dry-run, затем загрузку и независимую повторную сверку:

```powershell
python -m app.storage_migration_cli
python -m app.storage_migration_cli --execute
python -m app.storage_migration_cli --verify-only
```

Команда проверяет, что исходный файл находится внутри `UPLOAD_DIR`, вычисляет SHA-256,
загружает приватный объект с server-side encryption, сверяет размер и checksum через
S3 `HEAD`, и только после этого обновляет `storage_key`. Результат каждого файла
сохраняется в журнале и повторный запуск безопасен. Меняйте `STORAGE_BACKEND=s3`
только когда отчёт показывает `ready_to_switch: true`; локальные оригиналы команда
намеренно не удаляет до отдельного подтверждённого backup/retention-процесса.

## Резервное копирование и восстановление

На машине оператора должны быть совместимые версии `pg_dump` и `pg_restore`.
`DATABASE_URL` читается из окружения; пароль передаётся PostgreSQL только через
`PGPASSWORD` и не записывается в командную строку или манифест. Создать атомарный
custom-format dump вместе с SHA-256-манифестом:

```powershell
python -m scripts.backup_restore postgres-backup --output-dir D:\secure-backups\ai-garden
```

Каждый dump необходимо зашифровать и перенести в отдельное offsite-хранилище с
ограниченным IAM-доступом и политикой retention. Каталог `backups/` исключён из Git и
Docker context, но это не заменяет шифрование. Проверку восстановления выполняйте
сначала на отдельной staging-базе. Команда сверяет размер и SHA-256, а затем требует
точное имя цели; восстановление с `--clean` удаляет конфликтующие объекты:

```powershell
python -m scripts.backup_restore postgres-restore `
  --backup D:\secure-backups\ai-garden\gardener-20260715T123000Z-ab12cd34.dump `
  --confirm-target staging-db.example:5432/gardener_restore
```

Проверить обязательные настройки приватного S3 bucket и чтение метаданных образца:

```powershell
python -m scripts.backup_restore s3-audit --bucket private-ai-garden
```

Проверка требует IAM-разрешения на bucket versioning, encryption, public-access block,
lifecycle, listing и `HeadObject`. Команда возвращает exit code `2`, если хотя бы одна
защита не настроена. Restore drill PostgreSQL и тестовое восстановление выбранной версии
S3-объекта должны выполняться регулярно по эксплуатационному расписанию.

## Мониторинг и оповещения

`GET /metrics` отдаёт Prometheus-совместимый text format: количество и длительность
HTTP-запросов с ограниченными route labels, необработанные ошибки, состояния jobs,
ошибки AI, ожидающие уведомления, B2B-конверсии и сумму выставленных счетов. В
production endpoint требует отдельный Bearer `METRICS_TOKEN` длиной не менее 32
символов. Не используйте JWT пользователя как monitoring token.

Для критических ошибок можно задать HTTPS `ALERT_WEBHOOK_URL` и отдельный
`ALERT_WEBHOOK_SECRET`. Payload не содержит симптомов, фотографий или тела запроса,
подписывается HMAC-SHA256 и ограничивается по частоте через
`ALERT_MIN_INTERVAL_SECONDS`. Получателем может быть собственный alert gateway,
который уже маршрутизирует событие в Sentry, PagerDuty, Slack или другую выбранную
операционную систему.

## Чистый архив

Не добавляйте в Git `.venv`, `.env`, базы `*.db`, `uploads`, пользовательские
изображения и готовые ZIP-архивы. После коммита создайте архив только из файлов
репозитория:

```powershell
git archive --format=zip --output=AI_Garden_v1_clean.zip HEAD
```

Правила `.gitattributes` дополнительно исключают локальные данные из `git archive`.
